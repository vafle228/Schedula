# Onboarding: Schedula

Этот документ — карта проекта для нового разработчика. Цель: понять архитектуру, ключевые бизнес-концепции и то, как всё запускается, без необходимости читать весь код с нуля.

Schedula — десктопное приложение для методистов: автоматизация распределения учебной нагрузки между преподавателями и построения сетки расписания. Backend на Python (Bottle + SQLite), frontend — Vue 3 SPA, упаковка в exe через pywebview + PyInstaller.

---

## 1. Стек и как всё связано

```
┌─────────────────────────────┐        ┌──────────────────────────────┐
│  client/  (Vue 3 + Vite SPA) │  HTTP  │  server/  (Bottle app)        │
│  client/dist после build     │◄──────►│  /api/v1/*                    │
└─────────────────────────────┘        └──────────────────────────────┘
                 ▲                                    │
                 │  serves static + js_api bridge      │ SQLite (stdlib sqlite3)
                 └──────────── desktop/main.py ─────────┘
                          (pywebview native window,
                           Bottle запущен через Waitress
                           в фоновом потоке)
```

- **Backend framework — только Bottle.** `aiohttp` присутствует в `pyproject.toml`/`uv.lock`, но нигде не импортируется — мёртвая/аспирационная зависимость, не ориентируйтесь на неё.
- **Waitress** — production WSGI-сервер, используется только в desktop-режиме (`desktop/main.py`). При обычном `python server/main.py` работает встроенный dev-сервер Bottle (`debug=True`).
- **БД — чистый SQLite** через стандартный `sqlite3`, без ORM. Схема — DDL-строка + аддитивные миграции.
- **Frontend — Vue 3** (Composition API) + Vite. Роутинг — `vue-router` с hash-history (важно для работы из `file://`/pywebview). Стейт-менеджер — **самописный**, не Pinia/Vuex.
- **Python 3.14+** обязателен (`pyproject.toml`: `requires-python = ">=3.14"`) — в коде активно используются `StrEnum`, `X | None` и другие свежие фичи.

## 2. Структура backend (`server/`)

Чистая слоистая архитектура, всё собирается в одной точке:

```
server/api/routers/     → таблицы маршрутов (метод+паттерн → handler)
server/api/handlers/    → разбор HTTP-запроса, вызов сервиса, сериализация ответа
server/api/services/    → бизнес-логика, оркестрация репозиториев
server/core/models/     → доменные dataclass-модели
server/core/repositories/ → абстрактные ABC-порты (интерфейсы персистентности)
server/infrastructure/database/repositories/*_sqllite.py → конкретные SQLite-реализации
```

- **Composition root**: `server/api/routers/dispatcher.py` (`create_dispatcher`, строки ~71–182) — здесь и только здесь создаются все `Service(repo, ...)` и `Handlers(service)`, и регистрируются маршруты. Сервисы никогда не знают про SQLite напрямую — только про абстрактные порты.
- **Мини-роутер**: `server/api/routes.py` — регекс-роутер с захватом `:name`-сегментов, задуман как "честный порт" старого JS mock-роутера (чтобы контракт запросов не менялся).
- **Точка входа**: `server/main.py` — `build_api()` (строки ~80–124) собирает всё в один Bottle-app под `/api/v1/<url:path>`, ловит `ApiError` → JSON `{"error":{"message":...}}` с нужным статусом, отдельно обрабатывает `FileResponse` для бинарных `.xlsx`.
- **Ошибки**: `server/api/errors.py` — `ApiError(status, message)`, сообщение на русском и уходит напрямую на фронт как есть.
- **CORS**: разрешён `*` (нужно для Vite dev-сервера).

### Ключевые доменные модели (`server/core/models/`)

| Модель | Файл | Что это |
|---|---|---|
| `Teacher`, `TeacherConstraints`, `Absence`, `AbsenceType` | `teacher.py` | Преподаватель + ограничения расписания (жёсткие/мягкие занятые слоты, "методический день", макс. пар/день) + периоды отсутствия |
| `Discipline`, `Topic` | `discipline.py` | `Discipline` — предмет в связке (специальность, курс, период); `Topic` — раздел с типом занятия и кол-вом часов (единица, которой назначается преподаватель) |
| `Group` | `group.py` | Учебная группа, привязана к специальности/курсу, опциональный староста (`leader_id`), опционально ограничена по дням |
| `Lesson` | `lesson.py` | Конкретное занятие: либо *размещено* (неделя/день/слот заданы), либо *в пуле* (все `None`); *авто* (сгенерировано из назначения) или *ручное* |
| `Room` | `room.py` | Аудитория (`id` = отображаемое имя), есть `type` |
| `Assignment` | `assignment.py` | Связь `(group_id, topic_id) → teacher_id` + производное `pairs_per_week` |
| `Major` | `major.py` | Специальность, владеет группами |
| `AcademicYear`, `YearStatus` | `academic_year.py` | Учебный год (осенний+весенний диапазоны дат); активным может быть только один |
| `TopicType` | `topic_type.py` | Справочник типов занятий (`lec`/`prac`/`lab`/…) с цветом, коротким лейблом, длительностью в акад. часах |
| `SemesterSettings`, `Slot` | `settings.py` | Настройки сетки на (год, период): список звонков, активные дни недели, праздники, кол-во недель, длина акад. минуты |

### Репозитории и БД
- `server/core/repositories/*.py` — абстрактные ABC-порты (по одному на агрегат).
- `server/infrastructure/database/repositories/*_sqllite.py` — конкретные реализации.
  ⚠️ **Обратите внимание на опечатку в названиях файлов**: `_sqllite.py` (двойная "l"), а не `_sqlite.py` — это баг именования, зашитый в проект, ищите файлы по правильному написанию.
- `server/infrastructure/database/connection.py` — `connect()` включает `check_same_thread=False`, `row_factory=Row`, `PRAGMA foreign_keys=ON`.
- `server/infrastructure/database/schema.py` — DDL (`SCHEMA`) + аддитивная `_migrate()` для эволюции схемы без потери данных. Составные поля (слоты/праздники/ограничения) хранятся как JSON в `TEXT`-колонках.
- **Unit of Work**: `server/infrastructure/database/unit_of_work.py` — `SqliteUnitOfWork` открывает одно соединение, инициализирует схему и даёт по одному репозиторию-атрибуту на агрегат (`uow.teachers`, `uow.lessons`, ...).
- **Seed**: `server/infrastructure/database/seed.py` — при первом запуске (`uow.years.list_all()` пуст) наполняет БД демо-данными, портированными из старого JS mock'а.

## 3. Структура frontend (`client/src`)

- **Framework**: Vue 3 (Composition API) + Vite. Пакеты: `vue`, `vue-router` — и всё, никаких UI-библиотек и DnD-библиотек.
- **Entry**: `client/src/main.js` — ждёт `store.init()`, потом монтирует `App.vue` с роутером.
- **Router**: `client/src/router.js` — `createWebHashHistory()` (важно: hash-роутинг, т.к. приложение обслуживается статически из pywebview). 4 маршрута: `/distribution`, `/schedule`, `/directory`, `/settings`.
- **Стейт**: `client/src/store/index.js` — **самописный стор** на голых Vue 3 `reactive()`/`computed()`, экспортированный как singleton. Держит: текущий период (`fall`/`spring`), активный учебный год, справочники (годы/типы занятий/специальности/преподаватели/аудитории), учебный план (дисциплины/темы/назначения), слоты занятий, и **отдельные undo/redo стеки на модуль** (`planUndo/planRedo` для «Распределения», `schedUndo/schedRedo` — полные JSON-снапшоты массива занятий для «Расписания»). Все мутации идут через `client/src/api/index.js`.
- **API-слой**:
  - `client/src/api/client.js` — `request()` (fetch-обёртка над `/api/v1`) и `download()`, которая различает контекст: в pywebview зовёт нативный мост `window.pywebview.api.initiate_download` (диалог "Сохранить как"), в браузере — обычное скачивание blob'а.
  - `client/src/api/index.js` — по функции на каждый backend-эндпоинт.
  - `client/src/api/calendar.js` — **необычный кейс**: фронтенд-only клиент, который ходит напрямую в интернет (`isdayoff.ru` + `date.nager.at`) для синхронизации производственного календаря, минуя Python backend полностью.

### Views (`client/src/views/`)
- **`distribution/`** (модуль «Распределение», ~880 строк в `DistributionView.vue`) — пул карточек (группа, дисциплина), drag-and-drop назначения на преподавателя. Ключевые файлы: `useDistribution.js` (стейт drag'а: `dragKind`/`dragId`/`dragGroupId`/`dragOver`), `AssignMenu.vue` (клавиатурная альтернатива drag-drop), `CreateDisciplineModal.vue`, `AddTopicModal.vue`, `CurriculumExportModal.vue`.
- **`schedule/`** (модуль «Расписание») — `ScheduleView.vue` (~522 строки), `ScheduleGrid.vue` (~303 строки, сама недельная сетка), `useSchedule.js` (~317 строк — режим отображения группа/преподаватель/аудитория, текущая неделя, drag, выделение, модалки), `PoolPanel.vue` (нераспределённые занятия), `GenerationPanel.vue` (прогресс автогенерации), `LessonFormModal.vue`, `ConstraintsModal.vue`, `RoomsModal.vue`, `ScheduleExportModal.vue`, `ProblemsModal.vue`.
- **`directory/`** — справочник преподавателей/специальностей.
- **`settings/`** — настройки сетки семестра, синхронизация календаря (`HolidaysPanel.vue`).

### Drag-and-drop
Реализован на нативном HTML5 DnD API (`draggable`, `@dragstart`/`@dragover.prevent`/`@drop.prevent`) — сторонних библиотек нет. Смотрите `ScheduleGrid.vue` (`onCardDragStart`, `onCellDrop`) и `useDistribution.js`.

### Дублирование логики конфликтов
`client/src/utils/conflicts.js` — построчный порт `server/api/services/conflicts.py` на JS. Фронт даёт мгновенную/оптимистичную подсветку конфликтов при перетаскивании, backend — источник истины (эндпоинт `/schedule/conflicts`). Если меняете правила конфликтов — **не забудьте поправить оба файла**.

### ⚠️ Известная недоделка
`useSchedule.js` вызывает `store.togglePin(ids)` для закрепления слота ("Pin"), но в `client/src/store/index.js` такого метода нет. README и легенда сетки всё ещё упоминают функцию закрепления — похоже на незавершённую/удалённую фичу. Хороший кандидат на первую задачу.

## 4. Ключевая бизнес-логика

### Автогенерация расписания
- `server/api/services/generator.py`, `compute_generation()`.
- Это **жадный first-fit алгоритм**, не constraint-solver и не backtracking (в коде явно упомянуто, что раньше был solver на PuLP, теперь — нет).
- Занятия из пула сортируются по `number` (ручная подсказка порядка), затем лекции ставятся раньше практик. Каждому занятию ищется **самая ранняя свободная ячейка** в порядке (день → неделя → слот) — специально день во внешнем цикле, неделя во внутреннем, чтобы группа с малой нагрузкой держалась одного дня недели вместо размазывания по всей неделе.
- Два режима: `"rebuild"` (сначала снимает все неручные/неосиротевшие размещения) и `"fill"` (оставляет размещённое, рассаживает только пул).
- `ScheduleService.start_generation()`/`generation_status()`/`cancel_generation()`/`accept_generation()` (`server/api/services/schedule.py`) — оборачивают синхронное вычисление в фейковую асинхронную "джобу" с симуляцией прогресса для UI (`GenerationPanel.vue`). Реального фонового воркера нет.

### Обнаружение конфликтов и «осиротевшие пары»
- `server/api/services/conflicts.py`: `analyze()` — полный проход (источник истины), `slot_status()` — оценка одной гипотетической постановки (для hover-фидбэка при drag).
- **Осиротевшая пара**: занятие становится `orphan`, когда его `(group_id, topic_id)` больше не встречается в назначениях года — вычисляется в `LessonSyncService.enrich()` (`server/api/services/sync.py`). Осиротевшие занятия **никогда не удаляются и не переносятся автоматически** — только помечаются для ручной пересборки.
- Прочие типы конфликтов (severity `"hard"`, кроме отмеченного): преподаватель в двух местах одновременно, группа в двух местах одновременно, занятая аудитория, занятие вне активной сетки/недели, занятие в праздник, 2-часовое занятие в 1-часовом слоте, нарушение "методического дня", нарушение жёсткого недоступного слота, превышение макс. пар/день. Severity `"soft"`: нарушение мягкого (нежелательного, но допустимого) слота преподавателя.
- **Замены преподавателя**: `eff_teacher()` в `conflicts.py` учитывает `lesson.sub_by` — все проверки конфликтов идут по эффективному преподавателю, замена корректно освобождает слот основного и бронирует слот замещающего.
- **Синхронизация «назначение ↔ занятие»**: `server/api/services/sync.py`, `LessonSyncService._sync_pair()` — при (пере)назначении темы вычисляется `pairs_per_week` (`часы ÷ 2 ÷ число_недель`, округление, минимум 1) и создаются/удаляются строки `Lesson` под это число. **Уже размещённые занятия никогда не удаляются** — обрезается только избыток в пуле. Это и есть механизм "осиротевшие помечаются, а не удаляются молча".

### Экспорт в Excel (openpyxl)
Импорта из Excel **нет** — только экспорт. Шаблоны: `server/api/services/templates/curriculum_template.xlsx` и `schedule_template.xlsx`.
- **Экспорт учебного плана** (`curriculum_export.py`, `build_curriculum_workbook()`): загружает шаблон, сохраняет замороженную шапку (строки 1–18), перегенерирует тело с 19-й строки — по строке на (преподаватель, дисциплина), группировка по преподавателю с подытогом и итогом по кафедре, формулы вместо чисел (файл остаётся "живым" — пересчитывается в Excel).
- **Экспорт расписания** (`schedule_export.py`, `build_schedule_workbook()`): по листу на учебный день, блок на группу/преподавателя (в зависимости от `view`), 4-строчная ячейка на слот (дисциплина / тема+тип / аудитория / ФИО). ⚠️ В отличие от учебного плана, строится **с нуля через `openpyxl.Workbook()`**, а не из `schedule_template.xlsx`, несмотря на комментарий в шапке файла про "соответствие эталонному шаблону" — стоит перепроверить при следующей ревизии.
- `server/api/services/exports.py` (`ExportService`) хранит сгенерированные файлы **только в памяти процесса** (по id вида `ex1`, `ex2`, ...) до скачивания — на диск backend их не пишет.

## 5. Desktop-упаковка

- `desktop/main.py` — использует тот же `build_api()` из `server/main.py`, добавляет раздачу собранного `client/dist` (статика + SPA-fallback на `index.html`), запускает Bottle через **Waitress** в фоновом потоке, открывает нативное окно `pywebview` (`gui="edgechromium"` на Windows).
- `js_api` — экземпляр `DownloadApi` (`desktop/utils/download.py`), пробрасывается в JS как `window.pywebview.api`, даёт фронту нативный диалог "Сохранить как" для скачивания `.xlsx`. Внутреннее поле `_window` намеренно с подчёркиванием — иначе pywebview рекурсивно обходит все публичные атрибуты и уходит в бесконечный обход графа Qt-объектов.
- `schedula.spec` (PyInstaller, `pyinstaller schedula.spec --noconfirm`): собирает **onedir**-дистрибутив `Schedula/`. Бандлит собранный `client/dist` (падает с `SystemExit`, если не собран через `npm run build`), иконку (`desktop/static/icon.ico`), шаблонную БД (`server/schedula.db` → копируется рядом с exe при первом запуске), Excel-шаблоны, опционально `.env`. `console=True` сейчас (для отладки) — по комментарию в самом spec-файле для релиза нужно `False`.

## 6. Как запустить проект

**Backend отдельно (dev):**
```bash
python server/main.py
```
Поднимет Bottle dev-сервер на `127.0.0.1:8000`, БД создастся и засеется автоматически при первом запуске.

**Frontend отдельно (dev, с hot-reload):**
```bash
cd client
npm install
npm run dev
```
`vite.config.js` проксирует `/api/v1` на `127.0.0.1:8000` — поэтому нужно, чтобы backend уже был запущен.

**Полное desktop-приложение (dev):**
```bash
cd client && npm run build   # обязательно, иначе desktop/main.py не найдёт client/dist
python -m desktop.main
```

**Сборка exe:**
```bash
cd client && npm run build
pyinstaller schedula.spec --noconfirm
```

⚠️ Раздел «Быстрый запуск» в `README.md` устарел/аспирационен: там упомянуты `requirements.txt` и `python main.py --dev`, которых в проекте не существует. Ориентируйтесь на этот документ, а не на README.

**Переменные окружения**: `.env.example` в корне пуст (0 байт) — на сегодня в коде нет реального чтения `.env`/`os.environ`, зарезервировано на будущее.

## 8. Конвенции и особенности проекта

- **Язык кода — английский**, все идентификаторы (модули/классы/функции/переменные) на английском и в `server/`, и в `client/src/`. Русский встречается только в: пользовательских строках (тексты ошибок, лейблы UI), части докстрингов (объясняющих доменные правила) и **на 100% в сообщениях коммитов** (`git log` показывает исключительно русские сообщения — следуйте этой конвенции).
- **`server/CLAUDE.md`** — не специфичен для проекта, это общий гайд в духе "senior Python engineer" (PEP 8, тайпхинты, SOLID, докстринги) — это AI-инструкции, не архитектурная документация. `CONTRIBUTING.md` в проекте нет.
- **Опечатка в именах файлов репозиториев**: `*_sqllite.py` (двойная "l") вместо `*_sqlite.py` — не тратьте время на поиск "правильного" написания.
- **Архитектурная документация живёт в докстрингах**, а не в отдельных .md-файлах — модули `sync.py`, `conflicts.py`, `generator.py`, `schedule_export.py`, `curriculum_export.py`, `rollover.py` имеют необычно подробные докстринги, объясняющие "почему" — читайте их напрямую вместо поиска отдельного дизайн-документа.
- **Паттерн "честный порт"**: несколько backend-модулей (`conflicts.py`, `generator.py`, `sync.py`, мини-роутер) явно описаны как порты старого чисто-JS mock-бэкенда — это объясняет, почему логика конфликтов и генерации почти дублируется между Python и JS (`client/src/utils/conflicts.js`). Меняя одно — проверяйте, не нужно ли менять и другое.
- **aiohttp в зависимостях не используется** — не полагайтесь на него при чтении стека.

## 9. С чего начать (рекомендации для первой задачи)

1. Прочитать докстринги в `server/api/services/conflicts.py`, `sync.py`, `generator.py` — это фактическая архитектурная документация домена.
2. Запустить проект локально по разделу 6, потыкать оба модуля (Распределение / Расписание) вживую, сопоставить с UI-кодом.
3. Посмотреть на конкретный пробел — `togglePin` (раздел 3) — как первую небольшую самостоятельную задачу для знакомства со стором, `ScheduleGrid.vue` и `useSchedule.js`.
4. Если интересна тема тестирования — в проекте вообще нет тестов; можно начать с `conflicts.py`/`sync.py`, где легче всего словить регрессию незаметно.
